# Stalwart 0.16.27 → 1.0.0 migration

Supersedes Renovate PR operinko-labs/homeops#1927, which only bumps the image. 1.0
refuses to open a 0.16 store, so merging that PR on its own would crashloop mail.

Upstream guide: https://stalw.art/docs/migration/upgrade-0-16/

## What we run today (checked 2026-10-27)

| Thing | State | Migration impact |
|---|---|---|
| Version | v0.16.27 | Exactly the version `stalwart-migrate` requires |
| Data store | PostgreSQL DB `stalwart` on `postgres18` (`public` schema, ~1.5 GB) | Copied into a **new, empty DB** `stalwart_v1` |
| Blob store | `Default` (blobs in the data store, table `t` ≈ 843 MB) | Copied with the data; **no shared blob store**, so the 0.16 DB stays a clean fallback |
| Search / in-memory store | `Default` | FTS index is rebuilt by 1.0 after start; in-memory becomes local in-process (fine, 1 replica) |
| Directory | SQL directory with its **own** PG connection to DB `stalwart`, schema `directory` (41 accounts), shared with stalwart-users | Not migrated or touched; 1.0 keeps reading the same tables. The old `stalwart` DB must outlive 0.16 because of this |
| `Http.useXForwarded` | false | No reverse-proxy question in `prepare` |
| OIDC, AI models | none | No questions |
| WebUI | `LinkPhoenix/stalwart-webui-fork` latest (v1.3.2) | **Breaks**: 1.0 needs a 2.x bundle with a manifest, the fork has none → `/admin` would 404. Switch to official `stalwartlabs/webui` v2 at cutover |
| Domains (6) | ACME DNS-01, DKIM rotation and DNS publishing to Cloudflare, all `Automatic` | Any 1.0 instance with internet access acts on live DNS → the rehearsal pod gets no egress, and 0.16 and 1.0 never run at the same time |
| stalwart-users v0.4.0 | `x:Account/set`, `x:Account/query`, `x:Domain/query` + direct SQL on `directory.*` | No renamed fields it uses (`Domain.isEnabled→enable` is not read); verified in rehearsal |
| webui Job | `x:Application/*`, `x:Action/set UpdateApps` | Fields it uses unchanged; `Action` keeps `create` |
| Loki rules | match `delivery.rcpt-to-rejected`, `delivery.connect-error` … | Not in the renamed-events list; re-check log format after cutover |
| Image | Dockerfile identical apart from the healthcheck; enterprise build, uid/paths/ports unchanged | Use the standard (non-`-oss`) migrate tool |

Postgres headroom: 29 GiB free on the 40 GiB volume (the new DB adds ~2 GB, rehearsal ~4 GB
temporarily); 49 of 100 connections in use, so the migrate tool runs with `--concurrency 8`.

## Recovery routes

| When | Route | Data loss |
|---|---|---|
| Any time before 1.0 serves users | Revert the cutover commit → 0.16.27 on the untouched `stalwart` DB | None (the tool only ever reads the 0.16 DB) |
| After 1.0 has accepted mail | `stalwart-migrate rollback --forward-state …` into a new empty DB `stalwart_rollback`, start 0.16.27 on it | Queue, scheduled tasks and 1.0-only settings stay behind; DAV clients resync |
| Something above fails | Barman PITR of `postgres18` (WAL archiving to S3) or the on-demand `Backup` taken at T-0 | Since the backup |

The migrate state PVC and the `stalwart` DB are kept until the soak ends, because `rollback`
needs both.

## Phase 0 — preparation (no user impact, one commit)

1. `database-stalwart-v1.yaml`: CNPG `Database` `stalwart_v1`, owner `stalwart`, on `postgres18`.
2. `external-secret-v1.yaml`: a separate secret `stalwart-v1-secret` whose `config.json` points at
   `stalwart_v1` (`timeout` dropped: renamed `connectTimeout` in 1.0, default is fine). A separate
   secret, because a new key in `stalwart-secret` would make Reloader restart the running 0.16.
3. `migrate.yaml`: a `stalwart-migrate` toolbox Deployment (`ghcr.io/stalwartlabs/stalwart-migrate:1.0.0`
   via Harbor, `sleep infinity`, uid 2000) mounting the 0.16 `config.json` at `/etc/stalwart/config.json`,
   the 1.0 one at `/etc/stalwart-v1/config.json`, and a 1 Gi `stalwart-migrate-state` PVC at
   `/var/lib/stalwart-migrate`.
4. `prepare --non-interactive` to list open questions → answer them in `answers.toml`
   (expected: blob-store reuse = n/a, data categories = defaults **plus `queue` and `tasks`** so
   deferred outbound mail and calendar alarm tasks move with the final run). Review
   `prepare-report.txt` together.

**Done 2026-10-27** (c8b71a87). Answers: all categories except `telemetry`, OAuth registration
`accept` (no OAuth clients: Bulwark uses Basic auth), new permissions `grant`, changed defaults
`recommended`. The report has 2715 dropped objects, all expected: 2084 `MemoryLookupKey`
and the spam rules, tags, extensions and DNSBLs that duplicate 1.0's built-ins, plus 24 retired
`LLM_*` tags. The rest are removed permissions, `OidcProvider` registration flags and
`AcmeProvider.maxRetries`, and the custom WebUI URL warning.

## Phase 1 — rehearsal (no user impact, throwaway resources outside git)

Proves the final run, the 1.0 start and our integrations before the real window.

1. `pg_dump` the `public` schema of `stalwart` → restore into `stalwart_rehearsal_src`
   (a frozen copy, so `run --final` sees no moving counters while prod keeps running).
2. Separate state dir; `prepare` (copy the answers) → `run --final --yes` into `stalwart_rehearsal_v1`.
   Time it — this is the expected downtime.
3. Start a throwaway 1.0.0 pod on `stalwart_rehearsal_v1` with a `CiliumNetworkPolicy` allowing
   egress only to `postgres18-rw:5432` and kube-dns (no ACME, no Cloudflare, no outbound SMTP).
   No Service, port-forward only.
4. Checks: `/healthz/live`; admin login (recovery admin); a SQL-directory user login over
   IMAP/JMAP; stalwart-users' three JMAP calls (create + delete a test account); webui Job's
   `x:Application/get`; mailbox counts for 2–3 accounts vs 0.16; `report --severity warning`.
5. Delete the pod, both rehearsal DBs and the rehearsal state.

Go / no-go: all checks pass, no `error` rows, final run short enough for the window.

**Done 2026-10-27 — go.** Full final run from scratch took 2m16s, including a 25 s verify of
34 accounts with 0 mismatches. 1.0 started cleanly. Every API check passed, including the
stalwart-users create, query and destroy round trip, and the SQL directory still answers. Findings:

- Migrating `telemetry` leaves traces queued for indexing with no tracing store, so 1.0 logs
  `store.not-configured index=tracing` every 30 s. `telemetry` is now excluded, which is also the
  docs' default; with it excluded the log is clean.
- The webui Job's `x:Action/set` must use `@type`; with `type` 1.0 rejects it as `invalidPatch`.
  Fixed in the cutover PR.
- `Strategy not found: report` and the DNSSEC → DANE-disabled resolver warning already occur
  on 0.16. They are not regressions.
- The rehearsal pods and databases have been deleted.

## Phase 2 — bulk copy (no user impact)

`stalwart-migrate run` against live 0.16 into `stalwart_v1`, then `status` / `report`.
Repeat (incremental) any time; run one last time right before the window.

**Done 2026-10-27.** The first copy took 72 s and an incremental pass 2 s. Incremental passes
can be repeated at any time before the window.

## Phase 3 commands

```sh
# shorthand used below
M="kubectl -n mail exec deploy/stalwart-migrate -- stalwart-migrate"
ARGS="--concurrency 8 --source /etc/stalwart/config.json --target /etc/stalwart-v1/config.json"

# 1. backup
kubectl -n database create -f - <<'EOF'
apiVersion: postgresql.cnpg.io/v1
kind: Backup
metadata: {name: postgres18-pre-stalwart-1-0}
spec: {cluster: {name: postgres18}, method: plugin, pluginConfiguration: {name: barman-cloud.cloudnative-pg.io}}
EOF
kubectl -n database get backups.postgresql.cnpg.io postgres18-pre-stalwart-1-0 -w   # until completed (~3 min); plain `backup` is MariaDB's CRD

# 2. last incremental
$M run $ARGS

# 3. stop 0.16
flux suspend hr stalwart -n mail
kubectl -n mail scale deploy stalwart --replicas=0
kubectl -n mail wait pod -l app.kubernetes.io/name=stalwart,app.kubernetes.io/controller=stalwart --for=delete --timeout=120s

# 4. final run + checks
$M run --final --yes $ARGS
$M verify --full --source /etc/stalwart/config.json --target /etc/stalwart-v1/config.json
$M report --severity error
$M status

# 5. merge operinko-labs/homeops#1928 (un-draft first). The HR must carry the 1.0 spec
#    BEFORE it is resumed: resuming it with the old spec would bring 0.16 back on the old
#    DB, and mail delivered there would be missing from 1.0.
flux reconcile source git flux-system -n flux-system
flux reconcile ks stalwart -n mail          # applies the new HR spec; helm-controller stays suspended
kubectl -n mail get hr stalwart -o jsonpath='{.spec.values.controllers.stalwart.containers.app.image.tag}'   # must say v1.0.0
flux resume hr stalwart -n mail
kubectl -n mail logs deploy/stalwart -f     # then the step 6 smoke tests
```

## Phase 3 — cutover window (expected ~5 min of mail downtime: final run <1 min + pod stop/start)

Inbound SMTP during the window: haproxy on the VPS cannot reach Stalwart, senders get a
connection failure and retry (minutes to days), so nothing is lost. IMAP/JMAP/webmail clients
show errors until 1.0 is up.

1. `kubectl -n database create` an on-demand `Backup` of `postgres18`; wait for completion.
2. Incremental `run` (shrinks the final delta).
3. `flux suspend hr stalwart -n mail`, `kubectl -n mail scale deploy stalwart --replicas=0`, wait
   for the pod to go.
4. `run --final --yes` (asks for nothing more; watches 0.16 counters 30 s, copies queue + tasks,
   finalises, sample-verifies), then `verify --full` and `report --severity error`.
   **Stop here if any error is unexplained:** `kubectl -n mail scale deploy stalwart --replicas=1`
   and `flux resume hr stalwart -n mail` bring 0.16 back on its untouched DB (resuming alone
   does not restore the replica count). A later attempt then needs `run --force-after-final`, which
   is safe because 1.0 never served from the target.
5. Merge the cutover PR operinko-labs/homeops#1928: image `v1.0.0`, `config.json` mounted from `stalwart-v1-secret`, webui Job →
   `https://github.com/stalwartlabs/webui/releases/download/v2/webui.zip` (floating major tag);
   reconcile the ks, confirm the HR spec, then `flux resume hr stalwart -n mail`.
6. Smoke test: healthz; admin UI loads (`/admin`); IMAP login for one user; send to and from an
   external mailbox (DKIM pass, smarthost path); stalwart-users login + list; bulwark login;
   `x:IndexQueueStatus` shows the reindex progressing; ACME/DKIM state unchanged in the UI;
   no `ERROR` lines in the first 10 minutes; Loki rules still match the log format.

Rollback during the window = `git revert` of the cutover commit (+ resume). Once real mail has
landed in 1.0, use the `rollback` route instead.

## Phase 4 — soak and cleanup (~2 weeks, until ~2026-11-10)

- Expected user-visible effects: OAuth clients sign in again; DAV clients re-fetch once;

- After the soak: remove `migrate.yaml` (PVC goes with prune), the 0.16 `config.json` from `stalwart-secret`, and drop
